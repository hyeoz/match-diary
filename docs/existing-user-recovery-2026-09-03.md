# 기존 사용자 데이터 개별 복구 운영안

작성일: 2026-09-03

## 현재 결정

기존 사용자 데이터는 앱 시작 시 자동 복구하지 않는다. 지원을 요청한 사용자에게만 본인 확인 후 개별 `.matchdiary` 파일을 만들어 제공한다. 따라서 현재 운영에는 복구 API, AWS, App Attest 또는 Play Integrity가 필요하지 않다.

앱의 설정에는 `기존 기록 복구 요청`을 표시하고 정적 지원 페이지로 연결한다. 개인 복구 파일 자체는 GitHub Pages나 공개 저장소에 올리지 않는다.

## 요청 처리 절차

1. 사용자가 지원 이메일로 기존 기록 복구를 요청한다.
2. 운영자는 본인 확인에 필요한 최소 정보와 안전한 확인 방법을 개별 안내한다.
3. 보호된 원본 DB를 읽기 전용으로 조회해 해당 사용자 행과 연결 가능한 이미지만 추출한다.
4. 추출 결과를 앱 백업 규격인 `.matchdiary` 파일로 변환하고 체크섬을 검증한다.
5. 암호화된 파일 또는 짧게 만료되는 비공개 전달 수단을 이용해 요청자에게만 제공한다.
6. 사용자는 앱의 `백업 복원`에서 파일을 선택한다.
7. 제공 완료 후 중간 산출물과 전달용 파일을 삭제하고 최소한의 처리 기록만 남긴다.

닉네임, 응원 팀, 기록 날짜처럼 공개되었거나 추측 가능한 정보만으로는 본인 확인을 완료하지 않는다.

## 보류한 자동 복구 설계

기존 앱은 계정 대신 운영체제 기기 식별자를 사용자 키로 사용했다. 과거 백업 이력에 해당 키가 포함됐으므로, 사용자가 식별자만 입력하거나 일반 다운로드 링크를 받는 방식은 사용하지 않는다.

원래 앱을 사용하던 기기와 정식 앱 진위를 확인해 데이터를 한 번 가져오는 기술 구현은 향후 재검토용으로 보존한다. 현재 앱에서는 자동 실행 경로와 사용자 진입점을 제거했으며 서버를 배포하지 않는다.

## 자동 복구를 재도입할 경우의 앱 동작

아래는 현재 빌드에서 실행되지 않는 보류 설계다.

1. 앱 시작 후 로컬 데이터 초기화를 마치면 복구 가능 여부를 비동기로 확인한다.
2. iOS는 App Attest, Android는 Play Integrity로 정식 앱과 기기 무결성을 확인하고, 검증 토큰을 기기 식별자 해시와 복구 공개 키에 묶는다.
3. 기기 전용 X25519 키를 만들고 개인 키는 Keychain/Keystore 밖으로 보내지 않는다.
4. 서버가 해당 기기 식별자의 데이터만 `.matchdiary` v2 파일로 만든다.
5. 서버는 파일 키를 기기 공개 키로 감싸고, 본문은 인증 암호화한 청크로 전달한다.
6. 앱은 청크·전체 파일의 SHA-256을 검증하고 기기 안에서 복호화한다.
7. 검증된 기록만 SQLite에 병합한다. 서버 기록 ID의 유일 인덱스로 재시도 중복을 막는다.
8. 복구된 미래 일정 알림은 기기 알림으로 다시 예약한다.
9. 복구 성공 후 서버 임시 파일 삭제를 확인하고 완료 상태를 저장한다.

중단된 다운로드는 Keychain에 보관한 작업 ID와 토큰으로 이어받도록 설계했다. 현재 빌드는 이 경로를 호출하지 않으며 기존 로컬 데이터에 손대지 않는다.

사용자가 앱에서 전체 데이터 삭제를 실행하면 복구용 개인 키와 대기 작업도 지우고, 같은 과거 데이터가 자동으로 다시 들어오지 않도록 해당 기기의 자동 복구를 종료한다.

## 복구 데이터

- 프로필과 응원 팀
- 직관 기록과 연결 가능한 경기 정보
- 사진과 티켓 이미지
- 예약 정보
- 본인이 작성한 커뮤니티 글의 읽기 전용 사본

이미지 원본이 이미 사라진 경우 기록은 복구하고 누락 이미지 수를 결과에 포함한다. 다른 사용자 정보, 관리자 데이터, 서버 로그는 포함하지 않는다.

## 보류한 한시적 복구 서비스 코드

향후 자동 복구를 다시 검토할 때 사용할 수 있도록 다음 제한된 기능의 코드만 보존했다. 현재는 배포하거나 운영하지 않는다.

- 짧게 만료되는 1회용 challenge
- 앱 진위 검증
- 정확한 사용자 키에 대한 읽기 전용 SELECT
- 기기 공개 키 대상 암호화 파일 생성
- 소유 토큰이 있는 작업의 상태·청크 조회
- 완료 확인 후 임시 파일 즉시 삭제

사용자 목록, 검색, 수정, 일반 파일 URL, 관리자 복구 API는 없다. 작업 토큰은 원문이 아닌 해시만 저장하며 파일은 만료 시 정리한다.

## 자동 복구 재도입 시 필수 설정

현재 요청형 복구에는 아래 설정이 필요하지 않다. 자동 복구를 다시 도입하기로 결정했을 때만 다음 외부 설정과 검증을 모두 완료한다.

1. 보호된 환경에 복구 원본을 복원하고 지정 테이블 SELECT만 가능한 DB 계정을 만든다.
2. 복구 서비스를 Node.js 20 이상과 HTTPS로 배포하고 종료 시각을 설정한다.
3. Apple Developer에서 기존 번들 ID의 App Attest capability와 Team ID를 확인한다.
4. Google Cloud/Play Console에서 Play Integrity 프로젝트 번호와 배포 인증서 digest를 등록한다.
5. 앱 Release 빌드에 HTTPS 복구 URL을 주입한다.
6. 내부 테스트 기기의 실데이터 사본으로 본인·타인·중단·중복·만료 시나리오를 통과시킨다.
7. 복구 기간 종료 시 서비스와 읽기 전용 DB를 내리고 원본 보유·삭제 방침을 실행한다.

- iOS Simulator 네이티브 빌드 통과
