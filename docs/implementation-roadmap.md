# 직관일기 재운영 실행 로드맵 및 UI 디자인 전달 가이드

작성일: 2026-09-02  
상태: 5단계 핵심 기능 구현 완료 · 6단계 경기 일정 인프라 착수 가능

연관 문서: [무서버 개편 및 기존 사용자 데이터 복구 계획](./serverless-relaunch-plan.md)

프로젝트 기준선: [재운영 프로젝트 기준선](./revival-baseline.md)

## 1. 진행 원칙

- 기존 운영 서버를 먼저 다시 켜지 않는다.
- 공개된 기존 사용자 데이터의 보안 수습을 최우선으로 한다.
- 새 앱은 상시 사용자 데이터 서버가 없는 로컬 우선 구조로 만든다.
- 기존 앱에 기능을 계속 덧붙이기보다 재운영 브랜치에서 기반을 정리하고 필요한 기능만 이식한다.
- UI를 전반적으로 바꿀 경우 핵심 사용자 흐름을 먼저 디자인하고 화면 구현을 시작한다.
- 기존 사용자의 자동 복구는 새 로컬 데이터 형식과 백업 형식이 확정된 뒤 구현한다.
- 각 단계의 완료 조건을 통과해야 다음 단계로 이동한다.

## 3. 단계별 상세 계획

### 0단계: 보안 수습

목표는 기존 데이터를 안전하게 보존하면서 공개 접근과 추가 노출을 차단하는 것이다.

작업:

1. `match-diary-backend-express` 저장소를 비공개로 전환한다.
2. 공개 Git 이력의 DB 백업 파일을 별도의 암호화된 보관소로 옮긴다.
3. Git 이력에서 DB 백업을 제거한다.
4. DB, S3, 서버, 모니터링, 웹훅 관련 기존 자격증명을 교체한다.
5. S3 이미지의 공개 범위와 기존 URL 접근 정책을 점검한다.
6. 복구용 원본 DB와 이미지 목록의 무결성을 확인한다.
7. 누가 복구 데이터에 접근할 수 있는지 최소 권한으로 제한한다.

산출물:

- 암호화된 복구 원본
- 자격증명 교체 목록
- 공개 이력 정리 결과
- 데이터 수량과 이미지 누락 여부 리포트

완료 조건:

- 공개 GitHub에서 사용자 DB 원문을 조회할 수 없다.
- 기존 자격증명으로 운영 자원에 접근할 수 없다.
- 복구 원본을 별도의 안전한 위치에서 읽을 수 있다.

### 1단계: 프로젝트 기준선 확정

작업:

1. 앱스토어 운영 버전을 레거시 기준점으로 태그한다.
2. 기존 미커밋 변경을 별도로 보존하고 재운영 범위와 섞지 않는다.
3. `revival` 성격의 새 작업 브랜치를 만든다.
4. iOS bundle identifier, Android applicationId, 서명 키, 스토어 앱 식별자를 보존한다.
5. 기존 기능을 `유지`, `교체`, `제거`로 분류한다.
6. 현재 서버 API를 호출하는 모든 위치를 목록화한다.
7. 기존 AsyncStorage 데이터와 서버 데이터의 변환 규칙을 정리한다.

확정 기능:

- 유지: 기록, 사진·티켓, 캘린더, 승률, 히스토리, 지도, 공유, 알림
- 교체: 서버 저장, 서버 예약, 서버 일정 조회, 지도 WebView 의존
- 제거: 커뮤니티, AI 챗봇, 자체 회원 계정, 상시 원격 사진 저장
- 추가: 전체 백업, 복원, 기존 사용자 자동 복구

완료 조건:

- 새 버전에서 유지할 화면과 삭제할 화면이 확정돼 있다.
- 기존 앱의 스토어 업데이트 경로를 유지할 수 있다.
- 데이터 마이그레이션 입력과 출력 형식을 설명할 수 있다.

### 2단계: UX/UI 설계

UI 개편은 시각 스타일보다 사용자 흐름을 먼저 확정한다.

#### 2-1. 정보 구조

우선 검토할 하단 내비게이션 예시:

```text
오늘 기록 | 캘린더 | 기록 모아보기 | 직관 지도 | 설정
```

커뮤니티가 제거되므로 기존 탭 구조를 그대로 유지하지 않는다. `오늘 기록`과 `캘린더` 사이에서 같은 기록을 중복 편집하지 않도록 진입 규칙을 정한다.

#### 2-2. 필수 화면

- 시작 화면과 최초 설정
- 응원 팀 선택
- 오늘 기록 없음·있음 상태
- 기록 작성
- 사진·티켓 추가와 교체
- 경기·경기장 선택
- 기록 상세·수정·삭제
- 캘린더 월간 화면
- 직관 승률과 시즌 통계
- 사진 중심 히스토리
- 방문 경기장 지도
- 공유 이미지 미리보기
- 직관 예정 알림 설정
- 설정
- 전체 데이터 삭제
- 백업 생성
- 백업 복원과 충돌 처리
- 기존 기록 자동 복구

#### 2-3. 반드시 디자인할 상태

각 핵심 화면은 정상 상태 하나만 만들지 않고 다음 상태를 포함한다.

- 첫 사용·데이터 없음
- 로딩
- 오프라인
- 일정 갱신 실패
- 권한 거부
- 사진 파일 누락
- 저장 공간 부족
- 백업 파일 손상
- 복원 중 중복 기록
- 기존 데이터 없음
- 삭제 확인과 완료·실패

#### 2-4. 디자인 승인 기준

- 한 손 조작 시 주요 버튼에 쉽게 닿는다.
- 기록 작성 완료까지 불필요한 단계가 없다.
- 팀 컬러를 사용해도 텍스트 대비가 충분하다.
- iOS와 Android에서 동일한 기능 의미를 유지한다.
- 사진이 없는 기록도 자연스럽게 표현된다.
- 데이터 삭제·덮어쓰기·복원은 일반 동작과 명확히 구분된다.
- 글자 크기 확대와 긴 닉네임·메모를 견딘다.

### 3단계: 앱 기술 기반 정리

현재 React Native와 주요 네이티브 의존성의 간격이 크므로 UI 구현 전에 빌드 기반을 안정화한다.

작업:

1. 현행 React Native 기반으로 새 앱 셸을 만들지, 기존 프로젝트를 단계적으로 올릴지 기술 검증한다.
2. 기존 bundle identifier와 applicationId를 유지한다.
3. 불필요한 네이티브 권한과 패키지를 제거한다.
4. TypeScript, lint, 단위 테스트, 기본 화면 테스트를 CI에 연결한다.
5. APK, AAB, 빌드 산출물과 대용량 중복 파일을 Git 추적에서 제외한다.
6. 개발·테스트·스토어 빌드 설정을 분리한다.

완료 조건:

- 깨끗한 환경에서 iOS와 Android 기본 빌드가 성공한다.
- 기본 테스트와 lint가 통과한다.
- 앱에 비밀 키를 포함하지 않는다.
- 기존 스토어 앱의 업데이트 빌드로 서명할 수 있다.

#### 2026-09-02 완료 결과

- React Native 0.73.6 기준으로 재운영 앱 셸에 필요한 의존성만 남겼다.
- 자동 연결되는 네이티브 모듈을 AsyncStorage, SVG, Screens, Safe Area 네 종류로 축소했다.
- 광고, 위치 추적, 백그라운드 실행, 외부 저장소, 카메라 등 현재 셸에서 사용하지 않는 패키지·권한·설정을 제거했다.
- 앱에 포함되던 광고·지도 식별자 자리표시자와 iOS 임의 HTTP 허용 설정을 제거했다.
- TypeScript, ESLint, Jest 6개 테스트, 치명적 취약점 차단, Android 빌드, iOS 빌드를 실행하는 CI 워크플로를 추가했다.
- 잠금 파일 기반 `npm ci`, Android 클린 Debug 빌드, iOS 클린 Simulator Debug 빌드를 로컬에서 검증했다.
- Git에 추적되던 APK, AAB, baseline profile, release metadata와 오래된 iOS JS 번들을 제거하고 재생성 가능한 산출물로 분류했다.
- 기존 bundle identifier, Android applicationId, 버전, 조건부 release 서명 설정은 보존했다.

세부 변경과 검증 근거는 [앱 기술 기반 정리 결과](./technical-foundation-2026-09-02.md)에 기록했다.

### 4단계: 로컬 데이터와 사진 저장

이 단계에서 UI와 무관한 데이터 계약을 먼저 안정화한다.

작업:

1. 사용자 설정, 기록, 경기, 경기장, 알림, 백업 이력의 로컬 스키마를 정의한다.
2. 앱 내부에서는 화면이 DB나 파일 시스템을 직접 호출하지 않고 저장소 계층을 사용하게 한다.
3. 사진 선택 직후 앱 전용 영구 저장소에 복사한다.
4. DB에는 앱 저장소 기준 상대 경로와 파일 체크섬을 기록한다.
5. 기록 저장 실패 시 생성 중인 파일을 정리한다.
6. 기록 삭제 시 연결된 사진과 티켓을 함께 정리한다.
7. 기존 기기 AsyncStorage 형식이 남아 있으면 새 형식으로 변환한다.

테스트:

- 기본 사진 앱에서 원본 삭제 후에도 직관일기 사진 표시
- 앱 재시작 후 기록 유지
- 저장 도중 종료 후 데이터 정합성 유지
- 사진 교체·기록 삭제 후 고아 파일 없음
- 저장 공간 부족 시 기존 데이터 보존

#### 2026-09-02 완료 결과

- 프로필, 경기, 경기장, 기록, 사진·티켓, 알림, 백업 이력, 마이그레이션 로그를 포함한 SQLite v1 스키마를 구현했다.
- 화면의 AsyncStorage 직접 사용을 저장소·서비스 계층으로 교체했다.
- 선택한 사진과 티켓을 앱 전용 문서 폴더에 복사하고, DB에는 상대 경로·파일 크기·SHA-256 체크섬을 저장한다.
- DB 저장 실패 시 새로 복사한 파일을 롤백하고, 앱 시작 시 DB에 없는 고아 파일을 정리한다.
- 기록 삭제와 전체 기록 삭제 시 연결된 사진과 티켓을 함께 정리한다.
- 기존 UI용 AsyncStorage 키와 날짜형 레거시 기록을 멱등적으로 옮기되, 원본 키는 이 단계에서 삭제하지 않는다.
- 사진 선택, 기록 저장, 오늘·기록 화면 표시, 개별·전체 기록 삭제를 UI에 연결했다.

세부 구조와 검증 결과는 [로컬 저장 기반 구현 결과](./local-storage-foundation-2026-09-02.md)에 기록했다.

### 5단계: 핵심 기능 구현

다음 순서로 한 흐름씩 완성한다.

1. 최초 설정과 응원 팀 선택
2. 기록 생성·조회·수정·삭제
3. 캘린더와 경기 연결
4. 시즌별 승률·통계
5. 사진 히스토리
6. 방문 경기장 지도
7. 공유 이미지 생성
8. 기기 로컬 알림
9. 설정과 모든 데이터 삭제

각 기능은 서버를 끈 상태와 비행기 모드에서 검증한다.

#### 2026-09-03 완료 결과

- 로컬 일정 캐시를 기준으로 경기·상대 팀·시간·경기장을 자동 입력하는 기록 생성·조회·수정·삭제 흐름을 완성했다.
- 기존 달력 구조를 유지하면서 일정과 기록을 함께 표시하고, 선택한 경기에서 기록 작성과 직관 알림 예약으로 이동하도록 연결했다.
- 시즌별 직관 수·승률·승무패·방문 경기장 통계와 사진·티켓 히스토리를 구현했다.
- 외부 지도 SDK나 위치 권한 없이 로컬 경기장 좌표로 방문 경기장 지도를 구현했다.
- 기록 카드를 이미지로 생성해 운영체제 공유 시트로 전달하고, 기기 로컬 알림 예약·취소와 전체 데이터 삭제를 구현했다.
- TypeScript·lint·Jest 7개 스위트 17개 테스트, Android Debug 빌드, iOS Simulator 빌드와 실제 앱 실행을 검증했다.

세부 구조와 검증 결과는 [핵심 기능 이전 결과](./core-features-2026-09-03.md)에 기록했다.

### 6단계: 경기 일정 인프라

작업:

1. 공개 일정 전용 `match-diary-data` 저장소를 만든다.
2. 기존 크롤러를 DB 입력 방식에서 JSON 생성 방식으로 바꾼다.
3. 일정 JSON 스키마와 검증기를 만든다.
4. GitHub Actions 예약 실행과 수동 실행을 구성한다.
5. GitHub Pages로 검증된 JSON만 배포한다.
6. 실패 시 이전 정상 파일을 유지한다.
7. 앱에 `latest.json` 확인, 체크섬 검증, 시즌 캐시와 폴백을 구현한다.

완료 조건:

- 새 경기와 결과 변경이 앱에 반영된다.
- 잘못된 크롤링 결과는 배포되지 않는다.
- Pages나 Actions 장애 중에도 마지막 일정이 표시된다.

### 7단계: 백업·복원

작업 순서:

1. `.matchdiary` 백업 규격과 버전을 확정한다.
2. 기록과 이미지의 체크섬을 생성한다.
3. 전체 백업과 운영체제 파일 저장을 구현한다.
4. 임시 영역 검증 후 병합하는 복원 기능을 구현한다.
5. 중복 기록, 구버전 파일, 손상 파일, 저장 공간 부족을 처리한다.
6. 백업 생성·복원 중 앱 종료 상황을 테스트한다.

완료 조건:

- 백업 생성 후 앱 삭제·재설치·복원으로 기록과 사진이 동일하게 돌아온다.
- 복원 실패 시 기존 데이터가 손상되지 않는다.

### 8단계: 기존 사용자 자동 복구

새 백업 규격과 로컬 저장 방식이 확정된 뒤 시작한다.

작업:

1. 복구용 원본에서 사용자별 데이터와 이미지를 추출한다.
2. 원래 기기에서 기존 식별자를 확인하는 앱 흐름을 만든다.
3. 앱 진위 확인과 기기 전용 암호화 키를 적용한다.
4. 읽기 전용 복구 API에서 해당 사용자 데이터만 암호화한다.
5. 앱이 복구 파일을 받아 새 로컬 형식으로 가져온다.
6. 복구 결과 확인 후 서버 임시 파일을 삭제한다.
7. 운영 기간과 종료 후 원본 데이터 처리 방침을 실행한다.

완료 조건:

- 다른 사용자의 식별 정보를 입력해도 데이터를 받을 수 없다.
- 원래 기기에서는 본인 기록과 이미지만 복구된다.
- 복구 서비스에는 목록·수정·삭제 관리자 API가 노출되지 않는다.

## 4. UI 디자인 전달 방법

### 가장 권장하는 방식: Figma

Figma 파일 링크를 전달하고 다음 내용을 포함하면 바로 구현 사양으로 사용할 수 있다.

- 화면별 프레임과 이름
- 화면 간 이동을 보여 주는 프로토타입 연결
- 색상, 글꼴, 간격, 모서리, 그림자 등 디자인 토큰
- 버튼, 입력창, 카드, 모달, 탭 등 공통 컴포넌트
- 컴포넌트의 기본·눌림·비활성·오류 상태
- SVG 아이콘과 원본 이미지 자산
- iOS·Android에서 다른 동작이 필요한 부분에 대한 메모

개발용으로는 편집 권한이 필수는 아니지만, 레이어와 속성을 확인하고 자산을 내보낼 수 있는 열람 권한이 필요하다.

### Figma가 아직 없을 때

다음 중 편한 형태로 전달해도 된다.

- 손그림이나 종이 스케치 사진
- PNG·JPG 화면 시안
- 현재 앱 화면 위에 표시한 수정 요청
- 마음에 드는 다른 앱의 참고 화면
- 색상·분위기·폰트가 담긴 무드보드

완성 시안이 없어도 다음 다섯 가지만 전달하면 첫 디자인 방향을 잡을 수 있다.

1. 유지하고 싶은 기존 화면 또는 요소
2. 반드시 바꾸고 싶은 화면 또는 불편한 점
3. 참고할 앱 2~3개와 좋아하는 이유
4. 원하는 분위기를 표현하는 단어 3~5개
5. 로고, 팀 컬러, 기존 캐릭터·폰트의 유지 여부

예시:

```text
분위기: 야구장 티켓, 기록의 추억, 밝고 따뜻함, 너무 유아적이지 않음
유지: 팀 컬러, 폴라로이드 공유 이미지
변경: 복잡한 하단 탭, 기록 작성 단계, 오래된 모달 스타일
참고: 앱 A의 캘린더, 앱 B의 사진 기록 카드, 앱 C의 통계 화면
```

### 화면 시안에 함께 적어야 할 내용

이미지만으로 알기 어려운 동작은 짧게 메모한다.

- 버튼을 누른 뒤 이동할 화면
- 스와이프·길게 누르기 등 제스처
- 기록이 없을 때 보여 줄 내용
- 삭제·복원 확인 방식
- 사진 최대 개수와 대표 사진 규칙
- 경기 일정이 없거나 갱신에 실패했을 때 동작
- iOS·Android에서 다르게 보여야 하는 부분

### 자산 전달 형식

- 아이콘·단순 도형: SVG 우선
- 사진·질감 이미지: PNG, JPG 또는 WebP
- 움직이는 자산: Lottie 원본 또는 동영상 참고 자료
- 글꼴: 정확한 이름과 라이선스 또는 공식 다운로드 위치
- 색상: HEX 값과 밝은·어두운 배경에서의 용도

화면 캡처만 전달된 경우에도 구현은 가능하지만, 아이콘과 로고는 원본 파일이 있어야 해상도와 앱 용량을 안정적으로 관리할 수 있다.

## 5. 디자인 검토 순서

전체 화면을 한 번에 완성하기보다 아래 세 묶음으로 승인한다.

### 1차: 방향 확인

- 디자인 키워드와 무드보드
- 색상과 타이포그래피
- 하단 내비게이션
- 오늘 기록 화면
- 기록 작성 화면

### 2차: 핵심 기능

- 캘린더와 기록 상세
- 통계와 히스토리
- 지도와 공유 이미지
- 공통 컴포넌트와 상태

### 3차: 안전 기능

- 설정
- 백업·복원
- 기존 데이터 자동 복구
- 전체 삭제
- 오류·권한·오프라인 상태

각 차수에서 모바일 화면 캡처 또는 프로토타입으로 확인한 뒤 다음 묶음으로 이동한다.

## 6. 착수 시 첫 작업 묶음

실제 작업 시작 요청이 오면 다음 순서로 착수한다.

1. 기존 데이터 공개 상태와 복구 원본부터 안전하게 정리한다.
2. 앱 기준 버전과 서명·스토어 식별자를 보존한다.
3. 재운영 브랜치와 작업 체크리스트를 만든다.
4. 현재 화면과 기능의 기준 캡처를 남긴다.
5. 사용자에게 받은 디자인 자료를 화면 목록과 연결한다.
6. 정보 구조와 핵심 화면 와이어프레임을 확정한다.
7. 앱 빌드 기반과 로컬 데이터 저장의 기술 검증을 시작한다.

UI 디자인 자료가 아직 없어도 0~1단계와 앱 기반 기술 검증은 진행할 수 있다. 다만 본격적인 화면 구현은 최소한 하단 내비게이션, 기록 작성, 캘린더의 방향이 확정된 뒤 시작한다.
