# 직관일기 무서버 개편 및 기존 사용자 데이터 복구 계획

작성일: 2026-08-27  
상태: 기획안 — 구현 전

실행 순서와 UI 디자인 전달 방법은 [재운영 실행 로드맵 및 UI 디자인 전달 가이드](./implementation-roadmap.md)를 따른다.

## 1. 문서 목적

직관일기의 핵심 기능을 자체 운영 서버 없이 다시 제공하기 위한 개편 범위와 작업 순서를 정의한다.

이번 개편의 우선 목표는 다음과 같다.

1. 상시 서버와 데이터베이스 운영비를 없앤다.
2. 사진 앱에서 원본 사진을 삭제해도 직관일기 기록은 유지한다.
3. 사용자가 직접 전체 데이터를 백업하고 복원할 수 있게 한다.
4. 기존 서비스 사용자가 안전하게 본인 데이터를 회수할 수 있는 한시적 경로를 마련한다.
5. 보안과 개인정보 문제를 정리한 뒤 재출시한다.

## 2. 확정 범위

### 포함

- 기기 로컬에 직관 기록 저장
- 앱 전용 저장소에 사진과 티켓 이미지 복사·보관
- 캘린더, 직관 승률, 히스토리, 지도, 공유 이미지
- KBO 경기 일정과 결과 조회
- 기기 로컬 알림
- 전체 데이터 백업 파일 생성
- 백업 파일을 이용한 복원
- 기존 사용자 데이터의 일회성 복구

### 제외

- 앱에서 iCloud Drive 또는 Google Drive로 자동 동기화하는 선택 기능
- 경기장별 커뮤니티
- AI 챗봇
- 직관일기 자체 회원 계정
- 여러 기기 간 실시간 동기화
- 상시 운영되는 자체 API 서버
- 사진의 상시 원격 저장

## 3. 목표 구조

```text
직관일기 앱
├── 로컬 데이터베이스
│   ├── 사용자 설정
│   ├── 직관 기록
│   ├── 경기 일정 캐시
│   └── 백업 버전 정보
├── 앱 전용 파일 저장소
│   ├── 직관 사진
│   └── 티켓 이미지
├── 로컬 알림
└── 정적 데이터
    ├── 팀·경기장 기본 정보: 앱에 포함
    └── 경기 일정·결과 JSON: 정적 호스팅에서 갱신
```

앱의 핵심 데이터는 모두 기기 안에서 처리한다. 경기 일정과 결과만 정적 JSON으로 배포하며, 실행 중인 API 서버나 사용자 데이터베이스는 두지 않는다.

## 4. 사진 저장 원칙

사진 선택기가 반환한 사진 라이브러리 경로나 임시 파일 경로를 그대로 기록에 저장하지 않는다.

사진을 선택하거나 촬영하면 즉시 다음 순서로 처리한다.

1. 파일 형식과 크기를 확인한다.
2. 필요하면 방향 보정과 리사이징을 수행한다.
3. 앱 전용 영구 저장소에 새 파일로 복사한다.
4. 로컬 데이터베이스에는 복사된 파일의 상대 경로만 기록한다.
5. 저장이 완료된 뒤에만 기록 작성 성공으로 처리한다.

이렇게 저장한 사진은 사용자가 기본 사진 앱에서 원본을 삭제해도 유지된다.

다만 앱 삭제, 앱 데이터 삭제, 기기 초기화·분실 시에는 앱 전용 파일도 사라질 수 있으므로 백업 기능이 필요하다.

## 5. 백업 기능

### 백업 파일 형식

사용자가 하나의 파일로 전체 데이터를 보관할 수 있도록 한다. 확장자는 예를 들어 `.matchdiary`를 사용하되 내부 구조는 ZIP 기반으로 설계할 수 있다.

```text
matchdiary-backup/
├── manifest.json
├── records.json
├── images/
│   └── ...
├── tickets/
│   └── ...
└── checksums.json
```

- `manifest.json`: 백업 버전, 생성 시각, 앱 버전, 레코드 수
- `records.json`: 설정과 직관 기록
- `images/`: 직관 사진
- `tickets/`: 티켓 이미지
- `checksums.json`: 파일 누락·손상 확인용 체크섬

### 백업 동작

1. 사용자가 설정에서 `전체 데이터 백업`을 선택한다.
2. 앱이 데이터베이스와 이미지 파일의 정합성을 확인한다.
3. 임시 백업 파일을 생성한다.
4. 운영체제의 공유·파일 저장 화면을 열어 사용자가 원하는 위치에 저장한다.
5. 성공 또는 취소 후 앱 내부 임시 파일을 정리한다.

사진 용량이 커질 수 있으므로 백업 전에 예상 파일 크기와 여유 저장 공간을 안내한다.

## 6. 복원 기능

1. 사용자가 설정에서 `백업에서 복원`을 선택한다.
2. 운영체제 파일 선택기를 통해 `.matchdiary` 백업 파일을 고른다.
3. 파일 형식, 버전, 체크섬, 필수 항목을 검증한다.
4. 현재 데이터 유지 여부를 사용자에게 확인한다.
5. 별도 임시 영역에 먼저 복원한다.
6. 전체 검증이 성공한 경우에만 현재 데이터와 교체하거나 병합한다.
7. 실패하면 기존 데이터는 그대로 보존한다.

기본 정책은 `현재 데이터와 합치기`로 하되, 같은 기록 ID가 있으면 중복 생성하지 않는다. 전체 덮어쓰기는 위험성을 명확히 안내한 뒤 별도 선택지로 제공한다.

앱이 더 새로운 형식의 백업 파일을 읽을 수 없는 경우에는 임의로 복원하지 않고 지원 앱 버전을 안내한다.

## 7. 경기 일정·결과 제공

팀과 경기장 정보는 앱에 포함한다. 시즌 일정과 경기 결과는 연도별 정적 JSON으로 관리한다.

```text
schedules/
├── 2026.json
├── 2027.json
└── latest.json
```

앱은 다음 순서로 일정을 사용한다.

1. 기기에 캐시된 일정을 즉시 표시한다.
2. 네트워크가 있으면 정적 JSON의 버전을 확인한다.
3. 새 버전이 있을 때만 다운로드한다.
4. 다운로드나 검증에 실패하면 기존 캐시를 계속 사용한다.

경기 일정 수집 작업은 GitHub Actions 등의 예약 작업으로 실행하고 결과 파일만 정적 배포한다. 사용자 기록이나 식별 정보는 이 과정에 포함하지 않는다.

### GitHub Pages 호스팅안

경기 일정과 결과 JSON은 GitHub Pages로 제공할 수 있다. 예시는 다음과 같다.

```text
저장소: hyeoz/match-diary-data

https://hyeoz.github.io/match-diary-data/latest.json
https://hyeoz.github.io/match-diary-data/schedules/2026.json
```

무료 플랜을 사용하려면 저장소는 공개로 두고, 공개해도 되는 경기 일정·팀·경기장 데이터만 넣는다. 사용자 기록, 기기 ID, 사진 URL, 로그, API 키, 복구 데이터는 이 저장소와 Pages에 절대 올리지 않는다.

권장 저장소 구조는 다음과 같다.

```text
match-diary-data/
├── .github/
│   └── workflows/
│       └── update-schedule.yml
├── scripts/
│   ├── fetch-kbo-schedule.*
│   └── validate-schedule.*
├── schedules/
│   ├── 2026.json
│   └── 2027.json
├── schemas/
│   └── schedule.schema.json
└── latest.json
```

갱신 흐름은 다음과 같다.

1. GitHub Actions가 하루 1~2회 예약 실행된다.
2. KBO 일정과 결과를 수집한다.
3. JSON 스키마, 중복 경기, 팀·경기장 매핑, 날짜 형식을 검증한다.
4. 이전 데이터와 비교해 변경이 있을 때만 커밋한다.
5. 검증에 성공한 파일만 GitHub Pages에 배포한다.
6. 실패 시 기존 Pages 파일은 유지하고 수동 실행이 가능하도록 한다.

`latest.json`에는 스키마 버전, 데이터 생성 시각, 현재 시즌, 시즌 파일 경로와 체크섬을 둔다. 앱은 `latest.json`을 먼저 확인한 뒤 변경된 시즌 파일만 내려받는다.

GitHub Pages는 정적 파일 호스팅이므로 별도 서버 프로세스와 DB가 필요 없고 HTTPS를 지원한다. 현재 공식 제한인 사이트 1GB, 월 100GB 소프트 대역폭은 작은 일정 JSON과 현재 서비스 규모에 충분하다.

다음 운영 제약은 고려한다.

- GitHub Actions 예약 실행은 혼잡 시 지연될 수 있다.
- 공개 저장소에 60일 동안 활동이 없으면 예약 워크플로가 자동 비활성화될 수 있다.
- 예약 워크플로는 기본 브랜치에서만 실행된다.
- KBO 응답 형식이 바뀌면 수집기가 실패할 수 있다.
- 앱에는 마지막 정상 데이터와 출시 시점 일정 스냅샷을 남겨 장애 시에도 동작하게 한다.
- 시즌 시작 전과 포스트시즌 전에는 수동 검증을 진행한다.

기본 `github.io` 주소를 쓰면 도메인 비용도 필요 없다. 추후 브랜드 도메인이 필요할 때만 별도의 커스텀 도메인을 연결한다.

### 기존 웹 저장소 처리

기존 `match-diary-web`의 소개 페이지와 개인정보처리방침도 필요하면 GitHub Pages로 이동할 수 있다. 사용자 기록을 조회하던 지도 WebView는 새 로컬 구조와 맞지 않으므로 앱 내부 지도 또는 로컬 데이터를 전달받는 별도 정적 화면으로 교체한다.

일정 데이터는 웹 코드와 분리된 `match-diary-data` 저장소로 운영하는 것을 우선안으로 한다. 웹 화면 변경과 일정 갱신을 독립적으로 배포할 수 있고 공개 데이터의 범위도 명확해진다.

## 8. 기존 사용자 데이터 복구

### 현재 제약

기존 서비스는 이메일이나 로그인 계정 대신 기기 고유 ID를 사용자 식별자로 사용했다. 따라서 닉네임, 응원 팀, 요청 이메일만으로는 데이터 소유자를 안전하게 확인할 수 없다.

특히 데이터베이스 백업이 공개 GitHub 이력에 포함된 상태가 확인됐기 때문에, 사용자가 알려 준 기기 ID만 단순 비교하는 방식도 충분히 안전하지 않다.

다음 정보만으로는 데이터를 전달하지 않는다.

- 닉네임
- 응원 팀
- 기록 날짜나 경기장
- 사용자가 직접 입력한 기기 ID 문자열
- 요청 이메일 주소
- 사진 일부에 대한 설명

### 현재 복구 방식: 요청자 대상 개별 파일 제공

기존 사용자 데이터는 앱에서 자동 조회하지 않는다. 지원 요청을 접수하고 본인 확인을 완료한 사용자에게만 `.matchdiary` 파일을 개별 제공한다.

1. 앱 설정의 `기존 기록 복구 요청`에서 정적 지원 페이지를 연다.
2. 사용자가 이메일로 요청하면 운영자가 본인 확인에 필요한 최소 정보를 안내한다.
3. 보호된 원본에서 해당 사용자 데이터만 읽기 전용으로 추출한다.
4. 앱의 백업 규격으로 변환하고 체크섬과 포함 범위를 검증한다.
5. 암호화하거나 짧게 만료되는 비공개 수단으로 요청자에게 전달한다.
6. 사용자는 앱의 `백업 복원`에서 파일을 가져온다.
7. 전달용 파일과 중간 산출물을 삭제한다.

이 방식은 상시 복구 서버를 운영하지 않는다. 개인 복구 파일은 GitHub Pages나 공개 저장소에 게시하지 않는다.

### 개별 요청 시 보안 원칙

사용자가 고객지원으로 데이터 제공을 요청하더라도 이메일 첨부나 일반 다운로드 링크로 바로 전달하지 않는다.

- 본인 확인 전에는 데이터의 존재 여부나 내용을 회신하지 않는다.
- 본인 확인에는 공개되었거나 쉽게 추측할 수 있는 정보만 단독으로 사용하지 않는다.
- 확인 후에도 암호화된 백업 파일만 제공한다.
- 다운로드 링크를 사용하는 경우 짧은 만료시간과 1회 다운로드 제한을 둔다.
- 제공 완료와 실패 이력에는 최소 정보만 남긴다.

원래 기기를 분실·초기화했거나 기존 앱을 완전히 삭제해 기기 식별자가 달라진 경우에는 현재 보유 정보만으로 소유권을 신뢰성 있게 확인하기 어렵다. 이 경우 무리하게 데이터를 전달하지 않고 복구 불가 사유를 설명한다.

### 복구 파일 내용

- 사용자 본인의 프로필 설정
- 사용자 본인의 직관 기록
- 해당 기록의 사진과 티켓 이미지
- 사용자 본인의 예약 기록
- 사용자 본인이 작성한 커뮤니티 글의 사본
- 데이터 항목과 생성 시각을 설명하는 안내 파일

다른 사용자의 정보, 서버 로그, 내부 식별 정보, 관리자 데이터는 포함하지 않는다.

## 9. 기존 데이터 처리 전제

복구 기능을 구현하기 전에 다음 보안 조치를 완료해야 한다.

1. 공개 GitHub 저장소의 DB 백업 접근 차단
2. Git 이력에서 백업 파일 제거
3. 기존 DB 계정과 관련 자격증명 교체
4. S3 객체 공개 범위와 기존 이미지 URL 점검
5. 복구 원본을 암호화된 비공개 저장소로 이전
6. 사용자별 데이터 관계와 이미지 누락 여부 검사
7. 접근 기록과 임시 파일 삭제 정책 수립

원본 데이터는 복구 검증이 끝나기 전에 삭제하지 않는다. 복구 기간 종료 후의 보유·삭제 방침은 개인정보 대응 검토를 거쳐 별도로 확정한다.

## 9-1. 서버 저장소와 인프라의 최종 상태

장기 운영 시 기존 백엔드 애플리케이션은 필요하지 않다. 다만 즉시 삭제하지 않고 보안 수습과 기존 사용자 복구가 끝날 때까지 제한적으로 보관한다.

### 상시 남는 구성

- `match-diary`: 로컬 우선 모바일 앱
- `match-diary-data`: 공개 일정 JSON, 수집기, 검증기, GitHub Actions, GitHub Pages
- 정적 소개·개인정보처리방침 페이지
- 앱스토어와 플레이스토어 배포 설정

### 한시적으로 필요한 구성

- 암호화된 기존 데이터 원본 보관소
- 사용자별 데이터 추출 도구
- 요청자별 읽기 전용 추출 도구
- 본인 확인 절차와 임시 암호화 파일 전달 기능
- 복구 완료 확인과 임시 파일 삭제 작업

### 기존 저장소 처리

- `matchdiary-backend` Strapi: 현재 앱의 실제 데이터 API가 아니므로 필요한 자료를 보존한 뒤 보안 점검 후 아카이브한다.
- `matchdiary-backend-express`: 즉시 비공개 처리와 이력 정리가 필요하다. 일정 수집기와 데이터 추출 도구만 새 위치로 분리하고, 사용자 복구 기간 종료 후 런타임 서버 코드는 아카이브한다.
- `match-diary-web`: 소개·개인정보처리방침은 정적 호스팅으로 유지할 수 있고, 서버 기록에 의존하는 지도 코드는 제거하거나 교체한다.

따라서 재출시 후의 상시 인프라 개발은 `일정 수집·검증·정적 배포 자동화`가 전부에 가깝다. 기존 사용자 복구는 요청이 있을 때만 수행하는 종료일이 있는 운영 절차로 취급한다.

## 10. 삭제 기능

새 앱에서는 `모든 데이터 삭제`가 다음 항목을 한 번에 제거해야 한다.

- 모든 직관 기록
- 앱 전용 저장소의 사진과 티켓 이미지
- 사용자 설정
- 예약 알림
- 일정 캐시
- 백업 생성 중인 임시 파일

삭제는 모든 작업이 실제로 끝난 뒤에만 성공으로 표시한다. 일부 삭제에 실패하면 실패 항목을 알리고 재시도할 수 있어야 한다.

사용자가 앱 외부에 저장한 백업 파일은 앱이 자동으로 삭제할 수 없다는 점을 삭제 화면에서 안내한다.

## 11. 작업 순서

### 0단계: 보안 수습

- 공개 DB 백업 차단과 Git 이력 정리
- 데이터와 이미지 접근 권한 점검
- 기존 자격증명 교체
- 복구용 원본 데이터의 안전한 보관

### 1단계: 데이터 기반 교체

- 로컬 데이터베이스 스키마 설계
- 앱 전용 이미지 저장 모듈 구현
- 기록 생성·수정·삭제의 원자성 보장
- 기존 서버 API 의존 제거

### 2단계: 핵심 기능 이전

- 작성, 캘린더, 히스토리, 승률, 지도, 공유 기능을 로컬 데이터에 연결
- 알림을 완전한 로컬 알림으로 전환
- 커뮤니티와 AI 기능 제거

### 3단계: 일정 배포 자동화

- KBO 일정 수집기 정리
- 정적 JSON 형식 확정
- 공개 일정 전용 저장소 생성
- GitHub Pages 배포 구성
- 예약 갱신과 검증 자동화
- 실패 알림과 수동 실행 경로 구성
- 오프라인 캐시와 실패 처리 구현

### 4단계: 백업·복원

- 백업 파일 규격 확정
- 내보내기·가져오기 구현
- 손상 파일, 중복 기록, 저장 공간 부족 테스트
- 버전 호환성 테스트

### 5단계: 기존 사용자 복구

- 사용자별 데이터 추출 도구
- 앱의 복구 요청 안내와 `.matchdiary` 복원 흐름
- 본인 확인·비공개 전달·임시 파일 삭제 절차

### 6단계: 품질과 재출시

- 모바일 테스트 설정 복구
- lint와 의존성 보안 경고 정리
- iOS·Android 실기기 테스트
- 개인정보처리방침과 스토어 데이터 보안 항목 수정
- 비공개 베타 후 순차 배포

## 12. 완료 기준

- 백엔드가 중지된 상태에서도 기록 작성·조회·수정·삭제가 동작한다.
- 사진 앱에서 원본을 삭제해도 직관일기 사진이 유지된다.
- 네트워크가 없어도 기존 기록과 캐시된 일정을 볼 수 있다.
- 전체 백업 후 앱을 삭제·재설치해도 백업 파일로 복원할 수 있다.
- 복원 실패 시 기존 데이터가 손상되지 않는다.
- 사용자의 기기나 요청만으로 다른 사용자의 데이터를 조회할 수 없다.
- 기존 사용자 복구는 본인 확인 후 본인 데이터만 전달한다.
- 앱에 비밀 API 키나 서버 자격증명이 포함되지 않는다.
- 상시 운영되는 자체 사용자 데이터 서버가 없다.

## 13. 미결정 사항

- 로컬 데이터베이스로 SQLite 계열과 다른 저장 방식 중 무엇을 사용할지
- 백업 파일 자체에 사용자 비밀번호 기반 암호화를 기본 적용할지
- 기존 사용자 복구 서비스 운영 기간
- 원래 기기를 보유하지 않은 사용자에게 복구 불가를 어떻게 안내할지
- 기존 커뮤니티 글을 복구 파일에 포함할지 또는 별도 사본으로 제공할지

이 항목들은 구현 시작 전에 확정한다.
